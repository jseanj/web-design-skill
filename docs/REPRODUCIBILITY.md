# 如何检查这些案例与 Skill 的关系

## 当前证据状态

| 问题 | 当前能提供的材料 | 限制 |
| --- | --- | --- |
| 创作时使用了哪份规则？ | 仓库内技能快照、生成记录、SHA-256 指纹 | 指纹只证明文件一致性，不证明因果贡献 |
| 页面具体应用了什么？ | 每例的问题、方法映射、源码与交互 | 这是创作者的对应说明，仍可被质疑或复核 |
| 截图是不是对应网页？ | 本机浏览器截图、检查脚本、截图与源码指纹 | 后续可重新运行核对；不同平台字体可能不同 |
| 新会话能否复现？ | 十份可复制的复现简报与下方实验协议 | **尚未执行独立复现** |
| 比不用 skill 更好吗？ | 目前没有对照结果 | **尚未执行对照或盲评，不作提升幅度承诺** |

这些页面由一个创作会话完成：先读取技能入口、十种方法操作库与网页实现建议，再设计十个场景，制作页面、补充交互、检查与截图。共用 CSS/JS 属于本案例集的实现选择，不是技能对所有任务的要求。本轮根据反馈重读参考材料并重做构图，使用八份 image_gen 图片；图像与人工指导对结果都有贡献。随后将构图经验新增到技能参考文件，不能把完成版倒推成最初就存在的输入。

本仓库没有声称“给出一行提示词就一次生成了这些成品”，也没有把后续整理的简报冒充逐字原始输入。原始任务是创建十个用于开源展示的应用场景，期间用户提出了验证来源的问题。

## 逐案例检查

1. 从案例页进入“设计拆解”，确认它解决的问题。
2. 打开对应方法，检查设计动作是否与方法一致。
3. 阅读源码并操作页面：形态是否参与信息组织？关键内容是否保留？交互是否有真实的可观察变化？
4. 查看桌面和手机截图；对取景、阅读顺序与内容完整性做人工检查。
5. 运行 `python3 scripts/check_repo.py`，核对当前文件与发布版本指纹；只有主动修改交付文件后，才用 `scripts/manifest.py` 更新记录。可信的 Git 历史、提交签名和第三方运行记录能进一步帮助检查来源；当前哈希本身没有签名认证。

页面源码是完整交付；技能是生成时采用的工作规则。符合规则不意味着只有这个 skill 才能产生同类设计。

## 独立复现协议

若要公开宣称“别人也能用这个 skill 做出类似结果”，建议执行以下实验后发布原始记录：

1. 固定技能提交或指纹，选择一个模型与运行环境，记录准确型号、配置、日期和可用工具。
2. 新开一个没有本创作历史的会话，只提供技能文件和某个案例的复现简报。不要提供本案例截图、成品代码或补充答案。
3. 记录实际输入、工具调用、首版输出与后续人工干预。区分“首版”和“修改后版本”，不要只挑选成功结果。
4. 在允许范围内保存输出源码、桌面与手机截图，记录时间与资源消耗。
5. 按固定检查表评估：主题相关性、方法落实、信息完整性、阅读层次、响应式和主要交互。独立评审最好不知道是否使用了技能。
6. 在多种场景重复运行。允许外观差异；重点是能否落实同一种设计逻辑并完成任务，不要求像素一致。

这些步骤供未来执行；仓库中没有把未执行的实验填成“通过”。

## 若要检验 Skill 的增益

使用相同场景简报、模型、工具权限和资源预算，分别在两个全新会话中运行：一个提供技能，一个不提供。两组都不看现有成品，允许相同数量的修改。将匿名结果交给评审，按事先约定的标准打分，并公布失败案例与限制。

单个漂亮网页、一次成功复现或创作者自己的评分，都不足以证明普遍增益。对外介绍可以先使用“方法应用案例”“可操作概念页面”“提供复现材料”等准确表述。

## 布局骨架与装饰开关

布局骨架用于检查当前成品的主形、承载区和取景范围；第十例的装饰开关用于观察同一内容结构中的细节差异。两者都不是“有技能 / 无技能”的独立生成对照，也不证明效果增益。
